# 历史、上下文与记忆提取整改

日期：2026-10-24。对应 [Issue #10](https://github.com/iownmmiku/mikubot/issues/10)，修改保留在本地候选版本，尚未推送或发布。[Issue #9](https://github.com/iownmmiku/mikubot/issues/9)按用户后续要求暂缓，未修改侧边栏。

## 逐项处理

| 项目 | 本地修改与验证 |
| --- | --- |
| D1 默认24条消息导致衔接不足 | 默认按最近24个用户轮次选择，对齐用户轮开头；可在资源设置调整。明确追问“继续、后来、上次”等时，从最多200条更早候选中补充几个可撤销的原始片段，单独标为“上次话题衔接”，不额外调用摘要模型。40/80条历史经真实ChatService验证。 |
| D2 时间召回被指纹校验丢弃 | 时间选择器只返回规范原始记录，校验后才添加展示标签；不再改写或截断参与校验的content。端到端验证资料确实到达模型并进入来源记录。 |
| D3 摘要被裁剪但仍报告压缩成功 | 摘要与人设、当前请求共同保护，按整轮移除旧消息、按整块省略可选资料。摘要本身无法容纳时，重新用有效原文构建输入和来源清单，报告未压缩并记录原因；保存但未发送的摘要不写入本轮版本依赖。 |
| D4 小历史上限阻止压缩触发 | 摘要候选窗口与发送给对话模型的原文上限分离；达到阈值即允许整理，最高400条阈值也为轮次对齐预留空间。16条发送上限配合60/400阈值均有真实回复链路回归。 |
| D5 超长摘要静默丢弃 | 超过2400字符的硬限制后，最多进行一次收紧输出的重试，仍计入既有预算；未修复时保留有效旧摘要与原文，并记录失败原因。900字是提示目标，2400字符是接受硬上限，不把超长结果直接截成事实。 |
| D6 首次游标跳过早于一天的资料 | 首次从未处理的历史开始，按32条批次整理；旧版从未推进到消息ID的空游标可安全回填，保留此前失败记录与重试冷却。闲时轮询以有界分页轮转历史身份，不再只扫描24小时内活跃身份。已完成的游标不自动倒带；费用配额、审核和自动记忆开关继续生效。 |
| D7 排序不一致 | 历史合并、时间参考和提取统一采用created_at与SQLite插入顺序。提取游标保存消息ID，每次查询解析其当前rowid；同时间戳不按随机UUID排序。游标原消息删除时保守重看同时间戳资料，避免跳过未处理内容。 |
| D8 历史正文无标记截断 | 普通历史不再逐条切到5000字符，时间召回不切到600字符。超出整轮预算时省略完整旧轮次；检索参考块按完整消息取舍，并明确标注省略数量。15000余字符历史的末尾结论有回归。 |
| D9 孤儿助手轮 | 默认窗口和预算裁剪均对齐用户轮；移除问题时连同紧随的助手/工具回应一起移除。25—30条消息的奇偶边界均覆盖。 |
| D10 “最近”只取最新最忙一天 | 将指定时间范围分为4段，每段取首尾有界候选，避免同一繁忙日期挤掉更早约定；已遗忘来源在SQL取LIMIT前排除。五天前的约定与当天40条消息并存有回归。 |
| D11 遗忘消息堵住提取队首 | 在数据库分页前排除被屏蔽来源，不再先取32条再过滤。40条已遗忘消息加6条有效消息时，可直接提取后者并推进。 |
| D12 单边时间召回被读成新请求 | 对选中的用户消息补入紧随的助手回应，并重新校验来源。独立系统资料块明确标注时间、说话人、角色和不连续性，声明其不是本轮请求或执行授权。 |

## 兼容与性能

- 本地完整回归：1883通过、3跳过、0失败，254.57秒；新增历史专项23项和模型参数43项包含在全量中。最后补强的旧版失败空游标迁移与跨重启进度24项另行通过，不重复相加为全量数量。此前待办续写空标题失败已修复。完整范围见[测试报告](../TEST_REPORT.md)。
- 不修改既有消息正文、来源指纹或用户事实，也不默认开启付费摘要。新历史资料仍经过作用域、身份、来源撤回、记忆版本和权限校验。
- 新增时间检索和提取游标索引。数据库表结构及版本保持不变；旧schema-1备份可缺少这两项新增索引，恢复后重新建立。其他表、索引、触发器或视图仍按原规则严格校验；同名但定义不同的索引会被拒绝。
- 独立Windows/Python3.12合成数据：同一作用域14000条用户历史，7次采样。普通候选96条的暖查询中位数0.41ms，时间召回10.54ms，32条提取批次0.71ms；实际时间查询使用messages_origin_day索引。这是轻量本地查询测试，不能外推为真实QQ回复耗时、所有历史来源闭包或模型延迟。
- `tests/test_history_pipeline.py`覆盖真实Store、ChatService、ContextEngine与MemoryLifecycle，供应商使用录制输入的本地替身；未使用真实QQ或收费模型。

## 能力边界

默认窗口、时间采样与衔接片段都是有界选择，不是无限历史或“永远不会忘记”的保证。早期话题超出候选窗口、来源已撤回、任务所需资料无法容纳时，模型应承认缺少上文，不能补造经历。需要长期保留的内容仍应明确保存为可查看、可纠正的记忆。

时间窗口根据原消息的平台发送时间选择，缺失时参考接收/录入时间；插入顺序仅解决显示和游标的稳定排序，不替代事情发生时间。闲时旧消息回填逐批进行，受模型预算和审核控制，并非启动后立即重新蒸馏全部历史。
