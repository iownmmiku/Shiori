# 低内存 Linux / Docker 部署

本文描述当前源码（待发布0.1.6）的资源设置与可选部署方案；容量仍需目标机器验收。

本页提供可调的保守起点，不承诺 2 vCPU / 2 GiB 能同时承载任意数量的 QQ 群、图片或电脑任务。现有短时 Windows 空闲采样不能外推为 Linux 长期峰值；真实 QQ、真实供应商和连接器同机的容量需要在目标机器记录。

## 可选 Compose 覆盖

首次密码、持久卷、HTTPS 代理和连接器地址先按[部署与安全说明](DEPLOYMENT_AND_SAFETY.md)完成。然后使用两个文件启动：

```bash
docker compose -f compose.yaml -f compose.low-memory.yaml config --quiet
docker compose -f compose.yaml -f compose.low-memory.yaml up -d --build
```

覆盖文件默认给应用容器设置 **768 MiB 内存、1 CPU**，标准输出采用 `json-file`，每份日志 10 MiB、保留 3 份。这是尚待目标 Linux 压测确认的起点，限制过低会导致 OOM 重启，不会自动降低应用分配。用 `.env` 或启动时环境变量调整：

```text
SHIORI_MEMORY_LIMIT=768m
SHIORI_CPU_LIMIT=1.0
SHIORI_LOG_MAX_SIZE=10m
SHIORI_LOG_MAX_FILES=3
```

宿主回环映射 `127.0.0.1:8765`、非 root、只读根文件系统、`/tmp` 64 MiB、无新增权限及 128 进程限制继续生效。不要为方便连接器而挂载 Docker socket 或开放管理端口到公网。卷里的应用日志已有独立轮转；这里新增的日志限制针对 Docker 标准输出。

## 应用里的低负载起点

“设置与连接”的资源设置可以统一保存以下参数；不会修改供应商密钥。保留现有配置时也可逐项调整：

| 参数 | 试验起点 | 代价 |
|---|---:|---|
| 全部模型并发 / 等待 | 1 / 8 | 不同模型也会排队 |
| 每模型并发 / 等待 | 1 / 8 | 峰值请求更容易被明确拒绝 |
| 后台等待 / 每会话排队 | 4 / 2 | 学习任务和消息可能跳过 |
| 管理请求并发 / 等待 | 4 / 8 | 多窗口管理时等待增加 |
| 解析并发 / 等待 | 1 / 2 | 大文件按顺序处理 |
| 词项缓存 | 16 MiB | 更多检索需要重新分词；0 可关闭缓存 |
| 记忆检索并发 / 总在途上限 | 1 / 8 | 大型记忆库排队增加 |
| 每次召回 / 在线语义总等待 | 4 条 / 8 秒 | 语义不可用时使用 BM25 |
| 发送的历史消息上限 / 输入文字上限 | 16 条 / 16000 字 | 更早的原文可能省略；不限制摘要候选窗口 |
| 每次图片 | 1 张 | 超出时提示减少图片 |

每模型并发按**模型 ID**计算；全局模型并发才是全程序共享的限制。图片数和文字数分别控制，文字上限不包含图片的 Base64 数据。人设、本条请求、显式参考附件与实际工具定义共用文字预算，先为这些必要内容预留空间，再按完整轮次或资料块省略旧历史及可选召回。必要内容本身放不下时明确拒绝，不会截断任务要求、附件正文或静默禁用工具。

近期对话默认按24个用户轮次选择，还受发送消息数与文字预算限制。16条原文上限不会再阻止60条摘要阈值触发；摘要仍需全局与会话同时开启，并计入模型预算。摘要无法放进当前输入时改用有效原文，不报告未实际发送的压缩结果。具体边界见[历史管线说明](HISTORY_PIPELINE_AUDIT.md)。

语义总等待从当前回复开始检索时计时，由主查询和最多 3 个追加查询共用，包含语义锁、模型排队和查询向量；显式选择本轮等待构建时还包含记忆块向量。缺失记忆块向量默认在有界后台队列构建，仍会计费，详情见[大量记忆检索](MEMORY_RETRIEVAL.md)。到时继续使用已计算的词法结果，不保证整个回复在 8 秒内完成：本地检索 CPU、数据库读取和对话模型仍有各自耗时。显式“测试嵌入模型”仍使用该模型的请求等待设置。

新安装的语义检索和人格探索默认关闭。小机器可先保持关闭；表情包先关闭收集，必要时关闭发送；默认机器人配置里关闭自动记忆、黑话学习和表达学习，仍能显式保存记忆。关闭“定期记忆整理建议”可减少本地扫描。Planner 保留集中判断，先用 1500—2000 ms / 4 条消息，不必每条消息调用。

这些限制不是所有内存分配的统一上限。大型 ZIP、PDF、聊天图片和并发后台任务仍可能产生解析峰值。不要在高活跃群聊天期间同时执行多个人格蒸馏任务。

## 同机资源预算

分别采样操作系统、应用容器、NapCat/SnowLuma、可选电脑代码容器。为操作系统和连接器留出余量，不能将 2 GiB 全部分给 Shiori。QQ 客户端/连接器的版本、登录态和群活跃程度会改变占用，连接器没有在本项目里的统一内存保证。

内置 Docker 电脑脚本单任务已有 512 MiB / 1 CPU / 64 进程限制，属于额外开销；应用服务容器默认不挂载宿主 Docker socket，所以此覆盖文件不会自动启用它。电脑能力保持默认关闭。云端部署若调用远程模型，本地不加载模型权重；同机 Ollama 等本地模型需另外计算权重和上下文显存/内存。

## 无 QQ / 收费模型的检查

基础部署后，先保持 QQ、电脑控制、探索关闭，不填真实模型密钥。在宿主回环检查 `curl -f http://127.0.0.1:8765/healthz`，再使用正常 WebUI 登录验证首页、设置、显式记忆保存及检索。未配置模型时应有明确错误，不能将此误报为模型收发成功。已有本地替身回归可以验证协议，不代表真实 QQ 验收。

采样脚本只读取资源，不启动/停止容器、不改 Swap 或系统设置：

```bash
python scripts/sample_resources.py --container YOUR_CONTAINER --seconds 60 --output resource-idle.json
python scripts/sample_resources.py --pid SERVICE_PID --seconds 60 --output resource-process.json
```

先记录空闲，再记录文本队列、较大记忆、单图、语料解析以及真实连接器同机时的峰值。记录 Linux/Python/Docker 版本、实际限制、采样时长、记忆条数、群活跃程度，以及是否真实 QQ/模型。建议长期至少覆盖一次高峰和一次重连；本项目未将短时测试包装成长时间容量承诺。

`/proc/self/statm` 的 RSS、宿主 `MemAvailable` 和容器 `docker stats` 的内存口径不同，不能相加后当作独占内存。脚本中的 cgroup 字段来自运行脚本所在 cgroup，不会误认为指定 PID 的 cgroup。容器限制和 OOM 标记以该容器的 inspect 数据为准。

出现重启或卡顿时核对 `docker inspect --format '{{.State.OOMKilled}} {{.RestartCount}} {{.HostConfig.Memory}}' YOUR_CONTAINER`、`docker stats --no-stream`、应用日志，以及 cgroup v2 的 `memory.current`、`memory.peak`、`memory.events`。容器重建或重启可能重置计数；保存事故时间和采样口径。不要自动修改宿主 Swap、安全组或关闭鉴权。

内置统计兼容 cgroup v1/v2，使用两次采样间的真实累计 CPU 时间计算资源组使用率，首次显示采样中。资源组可能包含多个进程，进程指标仅涵盖 Shiori。可见祖先配额和 CPU 集合会约束分母，但不承诺在所有容器权限与挂载布局下都可采集。NapCat/SnowLuma 没有可信 PID 关联，独立资源明确显示未采集，可用上述宿主采样方法另行记录。
