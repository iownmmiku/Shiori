# 大量记忆与后台向量索引

本页描述 Shiori 0.1.4 的记忆检索与后台索引行为。

召回先使用独立 `memory_search.db` 的词项索引筛选候选，通常最多读取 192 条候选正文，再校验当前权限、记忆版本和来源依赖。旧记录中的稀有关键词也能被索引命中，不是只搜索最新记录。FTS5 不可用时降级为普通倒排索引；索引损坏会重建，不修改主记忆库。

每个进程首次检索需要分批建立词项索引，可能比后续请求慢；之后只刷新修改过的记录。备份恢复会使索引失效并重建。派生索引包含词项和检索元数据，应和数据目录一起保护；它不能绕过主库的授权校验。权限、共享范围或来源被撤销后，旧候选不会成为有效召回内容。

开启语义检索后，查询向量仍需要在线请求，默认由本条回复的多个查询共用 8 秒语义等待预算。**缺失的记忆块向量默认在后台生成**，本轮先使用词法结果和已存在的向量。后台最多等待 8 批，每批最多 12 个短片段，单个工作器顺序处理，先等待当前前台聊天结束；重复片段去重，单批模型等待最长 30 秒。后台请求仍受模型排队与每日费用预算约束，也会产生嵌入调用费用；超时的已发出请求仍保留消费待确认记录，不自动视为免费。前台优先指队列调度；已经发出的后台请求不会为新消息无条件中断，低并发配置下新到聊天仍可能等待。

在“设置与连接 → 资源与响应速度”可以选择后台构建或本轮等待构建。统计页可查看当前进程的排队、完成、失败与跳过数量。关闭软件会取消并等待工作器退出；队列不持久化，下次需要时再补建。清空索引、修改模型或撤销记忆权限会让旧任务失效。

已有向量按批次计算相似度，仅将前列候选的正文加入排序。数值扫描仍与已建向量数量相关，并非 ANN 索引；大文件的候选块处理也需要 CPU。语义预算用尽时降级词法，不能据此承诺整个回复耗时或 Linux 容量。

实现与验证均以本地协议替身为依据，未使用真实收费嵌入服务完成容量测试。
