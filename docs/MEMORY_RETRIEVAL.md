# 大量记忆与后台向量索引

本页描述当前 Shiori 0.2.1-beta 本地开发版的记忆检索与后台索引行为，尚未发布。

## 事件记忆

稳定事实和偏好仍单独保存；有过程的经历可以保存为事件，包含标题、概述、经过、参与者、地点与结果。自动整理每批最多提取两条事实或偏好、两件事件，依据原消息保留相关细节，不要求把经历缩成一句话，也不补造缺失信息。自动确认、候选审核、来源归属和每日模型预算继续生效。

事件使用可选 `episode` 结构；经过最多 3600 字，标题 120 字、概述 500 字、地点 200 字、结果 600 字，参与者最多 8 项、每项 80 字。各字段生成不超过 6000 字的标准正文，供现有分块词法与向量检索使用。短事实和旧版纯文本事件继续兼容，不自动给历史短句编造经过。

召回长事件时，在实际命中的片段之外保留标题、概述和结果。同一事件命中的多个片段先合并，再构建最长 2200 字的事件参考；总参考预算仍为 16000 字。超长事件明确标注仅展示摘要与匹配片段，完整经过保留在数据库和详情中。关系扩展最多两跳、每轮扫描 512 条边，避免大量旧关系拖慢回复。

事件发生时间与记录时间分别保存；原消息无法证明日期时标记“时间未确认”，不把整理当天当作发生日期。参与者只是原文称呼，不用来授予身份或权限。修改、删除、撤销共享和恢复备份仍通过主库版本及来源校验使旧召回失效。

详情页分页读取来源消息。新自动候选在服务端保存原消息指纹；来源已删改、跨会话、身份不符或已撤销时，不返回旧摘录。旧记录缺少指纹时显示无法核验，不回填伪造证据。手工录入的事件可无来源。

设计参考 [LivingMemory](https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory) 的事件与来源可追溯思路，当前实现独立编写，沿用 Shiori 的现有索引、权限和数据格式。

## 检索与后台索引

召回先使用独立 `memory_search.db` 的词项索引筛选候选，通常最多读取 192 条候选正文，再校验当前权限、记忆版本和来源依赖。旧记录中的稀有关键词也能被索引命中，不是只搜索最新记录。FTS5 不可用时降级为普通倒排索引；索引损坏会重建，不修改主记忆库。

词项索引在重启后保留，通过主库记录指纹校验并复用，不再每次启动重新分词。超过 64 条的首建、校验、大批修改及旧索引清理在后台分批执行；每批最多 64 条，目标约 40 毫秒后释放锁。构建期间先使用带作用域过滤的 SQL 召回，不等待整个索引完成。单条分词与 SQLite 提交不可强行中断，40 毫秒不是硬实时承诺；临时 SQL 路径仍随数据规模变慢。

普通修改或删除按 ID 增量更新；外部数据库修改、事务回滚及恢复备份后重新校验。关闭软件会停止并回收索引线程。派生索引包含词项和检索元数据，应和数据目录一起保护；它不能绕过主库的授权校验。权限、共享范围或来源被撤销后，旧候选不会成为有效召回内容。

开启语义检索后，查询向量仍需要在线请求，默认由本条回复的多个查询共用 8 秒语义等待预算。**缺失的记忆块向量默认在后台生成**，本轮先使用词法结果和已存在的向量。后台最多等待 8 批，每批最多 12 个短片段，单个工作器顺序处理，先等待当前前台聊天结束；重复片段去重，单批模型等待最长 30 秒。后台请求仍受模型排队与每日费用预算约束，也会产生嵌入调用费用；超时的已发出请求仍保留消费待确认记录，不自动视为免费。前台优先指队列调度；已经发出的后台请求不会为新消息无条件中断，低并发配置下新到聊天仍可能等待。

在“设置与连接 → 资源与响应速度”可以选择后台构建或本轮等待构建。统计页可查看当前进程的排队、完成、失败与跳过数量。关闭软件会取消并等待工作器退出；队列不持久化，下次需要时再补建。清空索引、修改模型或撤销记忆权限会让旧任务失效。

已有向量按批次计算相似度，仅将前列候选的正文加入排序。数值扫描仍与已建向量数量相关，并非 ANN 索引；大文件的候选块处理也需要 CPU。语义预算用尽时降级词法，不能据此承诺整个回复耗时或 Linux 容量。

实现与验证均以本地协议替身为依据，未使用真实收费嵌入服务完成容量测试。
