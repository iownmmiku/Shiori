# 记忆与上下文复查（2026-10-26，本地待发布）

本轮检查记忆提取、有效记忆召回、关系扩展、近期历史、时间检索、上下文压缩和管理接口。使用真实 Store、ChatService、ContextEngine 及本地模型替身复现；未连接用户服务器、调用收费模型或发送 QQ 消息。版本仍为 0.1.6。

## 复现与整改

| 问题 | 影响及处理 |
| --- | --- |
| 非空但畸形的提取候选推进游标 | 缺类型、坏来源或异常置信度可能让原消息被当作已完成整理。现先校验整批，再写入；畸形批次保留进度，合法空数组和低置信度结果仍可完成。 |
| 过期旧事实或关闭压缩后的旧摘要阻塞新提取 | 旧逻辑要求所有 active 旧记忆仍可用于聊天，尽管它们未进入提取提示词。现以 SQL 检查原有记忆版本及状态变化，原消息快照、暂停、权限和来源撤销继续独立检查。 |
| 入库排队时撤销自动记忆仍保存和采用 | 在线程事务内再次检查权限，在每项写入和提交前复核；中途撤权整批回滚。自动采用前再查版本和审核方式，用户后续更正保留，失效批次不推进游标。 |
| 已撤权共享来源的偏好让目标聊天持续失败 | 偏好查询补上与正式召回一致的来源权限回调，过滤已撤权来源，避免每次重试仍取回同一失效偏好。 |
| 关系召回每次读取全部关系与端点 | 改为按当前节点查相邻关系并分批验证，保留两跳、结果数量上限及端点身份、版本、来源检查。没有通过全库 LIMIT 丢弃后面的相关关系。 |
| 长参考数据直接截断 JSON | 按完整记录装入参考预算，省略数量随数据提供；不同类型保留排名顺序，不截残 ID 或 JSON。回复计划和已完成命令回执放入独立必要数据块，不随可选参考一起丢弃；必要数据超出整轮输入上限时明确停止模型派发。 |
| 时间检索与近期历史重复发送 | 在整轮输入预算处理后，按实际保留的消息 ID 去重，也去除两个参考块的重叠。预算已移除原文时保留检索副本，相同正文但不同 ID 的消息不合并。 |
| 摘要失效后原文恢复乱序 | 新覆盖列表按数据库时间和插入顺序保存；旧记录即使来自无序集合，恢复时也重新按规范消息顺序读取，再检查来源与权限。 |
| 关闭自动压缩后旧摘要衍生回复阻断聊天 | 上下文投影统一排除已关闭的自动摘要依赖，时间检索和话题衔接不再带入这些旧回复；有效原始消息和手动摘要继续按原规则使用。 |
| 上下文状态接口读取全部记忆 | 复用聊天实际选择有效摘要的路径，先按摘要属性过滤，再核验对应依赖，数据库工作移到工作线程。群摘要可能由同群其他成员的对话生成；管理状态与实际聊天选择保持一致。 |

## 验证边界

- 测试覆盖畸形输出、合法空结果、低置信度、原消息改动、在途撤权、整批回滚、审核方式变更和用户编辑；不通过清空记忆或重置额度使测试通过。
- 覆盖多轮摘要、旧无序覆盖列表、相同时间戳、缺失/异用户/异会话来源、压缩开关、手动摘要及实时撤销保护。
- 使用大量旧事实和不相关关系的合成数据检查读取范围。2000条无关关系的探针中，每次热召回读取并解码的记忆行由4008降为6，最大可见性投影参数由6001降为3；3000条旧事实下，提取保护无需加载全部旧正文。本机耗时不能外推为用户服务器的实际回复耗时。相邻关系查询仍使用 SQLite 过滤，并不保证所有数据规模下恒定耗时。
- 不修改既有记忆、隔离配置、每日上限或已消费额度。历史上已经推进的游标不会自动回退；旧数据是否因当时的模型格式问题漏提取，不能仅凭现在的记忆总数还原。
- 本轮没有重新验收线上记忆增长或真实模型的提取质量。服务器部署与自然聊天验证需要另外进行。
