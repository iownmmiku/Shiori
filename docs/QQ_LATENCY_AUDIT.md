# QQ慢回复排查

## 2026-10-24 服务器更新后的私聊回归

部署测试版后的两次私聊分别约303.3/333.8秒生成答复，约337.8/384.8秒完成文字发送；实际模型排队约1毫秒，模型阶段约75.4/59.4秒。耗时没有全部落在原有分段测量里，不能将增加的本地等待归因于上游。

以生产数据库隔离副本分析：该私聊7882条记忆，近期96条候选，旧回复传递361项消息来源和675项记忆版本。历史逐条调用`_changed`，每个记忆又单独`memory_accessible`重建投影、复制设置和读取会话；12秒采样已调用3254次单项投影。来源图按每个历史根重复遍历，在12秒内调用约64万次递归。每个流式分片还会重新进行675次单项投影，单次约2.2秒。这解释了扩大历史候选后产生的性能回归。

本次修复：单次历史读取共享一份批量权限投影；每次发送校验仍重新读取当前状态。来源图只在当前核验调用内复用节点读取与验证结果，撤回、编辑和跨调用重验不使用旧缓存。消息存在性/作用域用有界SQL批量检查，不解码历史正文。

同机隔离副本、带cProfile的单次结果：历史候选读取299.29毫秒，单次记忆版本复核82.27毫秒，消息存在性3.97毫秒，来源图766.58毫秒；修复前历史与来源图各在12秒诊断期限内仍未完成。保留24轮历史，不靠缩回旧窗口或丢弃依赖来加速。

新增回归覆盖重叠依赖批量读取、外部数据库编辑即时撤回、来源作用域/墓碑、环形来源、原文篡改及失败图不能泄漏部分闭包。本地完整回归1906通过、3跳过；服务器独立源码回归194通过、2跳过。阶段样例不等于整轮QQ时延：当前上游仍有几十秒生成等待，需要依据后续真实私聊日志确认端到端效果。

服务器运行0.1.5，4核、约4GB内存；检查时进程RSS约149MB，可用内存约1.4GB，负载约1.05。当前快照没有内存耗尽证据，不能据此排除历史高峰。

- 没有启用待发布的消息防抖；上下文压缩关闭，所以不能把本次分钟级等待归因于这两项。
- 当前QQ私聊生效配置为`always_reply=true`，直接跳过Planner。群聊仍开启Planner。
- 生效的机器人配置把QQ聊天指定为`gemini-3.8-flash`；全局默认对话路由虽为`deepseek-v4.1-flash`，不会覆盖这项明确的机器人配置。Planner、记忆和整理仍共用全局DeepSeek模型。
- 单模型并发1、全局模型并发2。记忆每累计6条消息可触发一次后台提取。

## 已确认的程序瓶颈

### 模型调度队头阻塞

`Provider._provider_slot`先占全局槽，再等单模型槽。同模型第2个请求排队时也能占掉全局第2槽，挡住其他型号的前台请求。后台已派发的提取、识图或蒸馏又不能被前台抢占。

离线用真实调度器复现：A模型运行300毫秒，第二个A请求排队，无关B模型也要等到约316毫秒才能进入。模拟后台识图300毫秒，同型号聊天等到约310毫秒。服务器确实采用单模型1/全局2的配置，具备该问题的触发条件；历史账本没有队列时间，不能给每次线上等待精确归因。

### 记忆权限检查随流式分片反复全扫

服务器共有13993条有效记忆，最大私聊作用域7882条、记录JSON约4.1MB。只读执行当前来源墓碑查询，一次约43.21毫秒；另一个2071条会话约12.74毫秒。

`receive_chat`每个网络分片同步检查`before_send`；其来源检查反复调用`blocked_memory_sources`，扫描该作用域的记忆及黑话JSON。即使墓碑为空也会扫描。数百个小分片能够积累明显的同步CPU开销，并阻塞同一事件循环里的其他聊天及QQ回执处理。

离线用13993条短记忆、9个作用域、8条引用和24条历史重现，单次完整`before_send`中位37.81毫秒。该样例的模型完成后收尾约67毫秒，因此不能仅凭此把线上保存前5—9秒全部认定为最终权限校验；还需要测量事件循环与锁等待。优化必须保留撤权、删除、来源和版本检查。

### QQ逐段回执等待

程序逐段等待连接器成功回执，段间配置为600毫秒。实测多段回执之间远超600毫秒，近两小时日志出现第2段和第4段`TimeoutError`，因此配置的段间间隔不能解释全部等待。

等待回执及超时停止用于避免送达未知时重复发送。不能直接移除回执验证或自动重发来掩盖延迟。应分别记录派发时刻、连接器响应时刻和本地处理时刻，区分连接器/QQ慢与本机事件循环饥饿。

### 表情选择占住下一轮文字回复锁

`ConversationFlow._flush`持有同会话同用户锁，文字发完后仍等待`stickers.choose`调用模型。离线把选图延迟设为200毫秒，下一轮`chat.respond`也被完整阻塞200毫秒。线上发送概率为0.1，因此属于间歇性放大因素，而非每条必然发生。

## 额外的浪费与边界

- 检查窗口内有48次输出额度耗尽事件：Planner 28次、记忆提取20次；样例Planner的350输出Token全用于思考，没有正文。另有53条备用模型切换事件。此统计不能推断为48次聊天失败；它说明后台及判断调用存在重复生成浪费，并增加队列压力。
- 群聊Planner的`max_age_ms=15000`只是返回后判断是否过期，不是15秒硬超时。离线设置50毫秒有效期，模拟模型200毫秒，仍约218毫秒才返回。当前私聊必回已跳过Planner，不能用这一项解释本次私聊样例。
- 语义检索已有共用8秒期限，后台建文档向量。服务器仅有1783条1024维缓存向量，不能套用离线8000向量扫描5.5秒的结果来断言线上向量检索耗时。
- SSE拿到完整choice的结束标志后仍等待usage尾部/`[DONE]`或EOF，可能再增加中转尾部等待；当前数据没有逐阶段时间，尚未证明它占据多少线上耗时。
- 同一群的`ChatService`仍用作用域锁串行整轮生成；图片标识解析和下载也可能串行等待。本次统计以普通私聊为主，不将这些条件性路径当成已发生事实。

## 修复优先级

1. 补充接收、排队、召回、请求派发、首字、完成、QQ逐段派发和回执的阶段耗时，队列时间单独记录。
2. 修复全局/单模型取槽顺序，避免等待者占住其他模型的全局容量，给前台预留派发机会。
3. 将来源墓碑和依赖检查改为有界查询或按数据修订失效的索引，保留每次派发与输出的实时权限复核。
4. 表情选择移出文字会话锁，设短且可放弃的时限；当前会话变化后丢弃过期表情。
5. 根据真实QQ回执阶段定位连接器耗时；Planner与提取使用合适的模型和额度，避免只思考后耗尽再切备用模型。

以上是修复前的只读诊断，完整脱敏数据保存在本机忽略文件，不包含聊天正文、账号明文或密钥。后续本地修复见下节；服务器尚未部署这些修改。

## 2026-10-24 本地修复

- **原子调度**：等待中的请求不持有任何模型容量，同时获得全局、单模型和后台槽位才派发。就绪的前台请求优先，同优先级按顺序，跳过暂不可用的模型；不抢占已派发的请求。保留各层队列上限、取消清理和派发前后的实时权限校验。
- **来源校验缓存**：最多缓存128个作用域，TEMP触发器跟踪记忆/黑话的增删改及作用域移动；事务内不使用共享缓存，避免回滚后修订号复用。外部连接提交通过`PRAGMA data_version`双检失效，恢复备份重建跟踪。消息与用量入库不触发无关的整表JSON扫描，返回值为副本。
- **表情包不阻塞文字**：独立可取消任务，每个作用域至多一个、全局至多128个尚未结束的任务。5秒仅限制选择模型，已派发图片继续等待连接器原有回执。新消息、来源清除、权限变化或人格编辑后丢弃旧图；文字ACK期间收到新消息，也不能在旧文字发完后启动过期选择。关闭时回收任务。
- **Planner硬期限**：`max_age_ms`覆盖知识查询、模型槽位和网络请求，不再等长请求返回才判过期。超时保持本轮不回复，直接触发按现有规则反馈；已派发但被取消的消费继续明确记为待核实，不将它当作免费请求或自动重发。
- **阶段测量**：模型用量增加`queue_wait_ms`，旧`latency_ms`语义保持不变；排队取消和超时也进入当前轮阶段耗时。QQ消息记录`chat_timing`、`qq_reply_timing`以及逐段`qq_sent`/`qq_delivery.send_timing`，可按作用域、逻辑回复编号和`trace_id`关联。包括作用域锁等待、记忆召回、上下文构建、模型调用、文字发送、socket写入、连接器回执等待及回执接收后本地恢复执行时间。嵌套阶段会重叠，不能相加；回执接收时刻是本地解析该帧的时刻，不等于网络抓包到达时刻。

本地8000/14000条记忆的来源检查样例，单次扫描约13.9/26.3毫秒，预热后约0.008毫秒；连续200次预热检查没有重复执行JSON扫描。该结果只衡量来源检查函数，不能描述为整轮聊天速度或服务器上的实测提升。
